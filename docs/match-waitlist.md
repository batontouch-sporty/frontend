# 매치 상세 대기 등록·취소 (frontend #34)

기준 main: `521c6b7`. backend #35의 A18 POST `/match-service/api/matches/{matchId}/waitlist`, A19 DELETE `/match-service/api/matches/{matchId}/waitlist/me`를 사용한다. 공통 Axios 인터셉터가 인증과 Gateway 서비스 경로를 적용한다.

- 정원이 찬 CLOSED 모임에서 시작 전 비방장·비참가자만 신청 가능하다. 서버 LocalDateTime은 KST(+09:00)로 판단한다. 최종 자격·정원 검사는 서버가 담당한다.
- 등록은 201의 matchId·양의 정수 position을 확인하고 신청 당시 순번만 표시한다. 실제 참가 확정으로 표시하거나 참가자 수를 늘리지 않는다.
- 대기 상태 GET은 현재 계약에 없다. 새로고침 시 대기 여부를 단정하지 않고, 기존 신청자를 위한 취소 동작을 제공한다. 현재 순번을 임의 계산하거나 localStorage를 서버 상태처럼 사용하지 않는다.
- 취소는 확인 후 204를 받고 상세를 재조회한다. WAITLIST_NOT_FOUND는 이미 승급됐을 수 있으므로 참가 상태를 재조회한다. 취소·완료 모임과 방장·참가자에게는 대기 행동을 제공하지 않는다.
- 일반 참가/탈퇴/삭제와 같은 busy ref와 pending 상태를 공유해 요청 중 연속 클릭·교차 실행을 차단한다. 페이지 이동 뒤의 늦은 응답은 무시한다.
- 로그인 필요/만료 시 원래 상세 경로로 복귀한다. 409 기존 대기는 순번을 만들어내지 않고 취소를 제공한다. 서버/네트워크 장애의 불확실한 결과를 성공으로 표시하거나 자동 재신청하지 않는다.

## 검증

- 전체 Jest 40개 파일, 464개 테스트 통과. API 201/204·오류 응답, 중복 클릭, 미로그인·401, 기존 대기, 승급/취소 경합, 불확실한 응답, 페이지 이동, 상태·시간·권한 제한을 포함한다.
- `npm run build` 성공.
- 브라우저에서 로컬 테스트 응답을 사용해 비로그인→로그인→원래 상세 복귀→대기 등록→신청 당시 2번 표시→취소 확인→상세 재조회·재신청 버튼 복귀를 확인했다. 모바일 폭에서도 확인했다.
- 이번 실행에서는 실제 Gateway·DB·Kafka를 연결한 프론트 E2E는 수행하지 않았다. 로컬 테스트 응답은 저장소 코드에 포함하지 않는다.

## R10과의 경계

A29·상태 스케줄러·포인트 DDL·생성/참가/승급 Saga는 변경하지 않는다. backend #85의 R10 적용 때 API 상태 코드·참가/승급 상태 계약이 변경되면 별도 연결 검증이 필요하다. DDL을 기다리지 않고 현재 확정 A18·A19 화면 연결을 진행한다.
